# Kosm - Design

> κόσμος: *order, arrangement, adornment*. The root of both *cosmos* and *cosmetic*.
>
> **Kosm** is the tool. A **kosmos** (pl. **kosmoi**) is a rice. The dotfiles holding every
> kosmos are the **Ktisis** (κτίσις, *creation*).

This file holds what guides new work: goals, the architecture, the rules every app and
adapter follows, and non-goals. How something already built works is in its code, doc
comments, tests and README. Work still to do is in `TODO.md`; anything neither here nor
there is undecided, so ask.

## Goals

- **Kosm configures the whole system,** not only its looks: settings several programs share (keyboard layouts, cursor, rounding) are set once like colors are.
- **A minimal kosmos is tiny.** One official base holds every supported app with plain defaults; a look makes it look nice; a user's kosmos picks a base and a look and sets the few things that are personal. Every app derives the rest.
- **Depth is opt-in, in the same file.** Any single value of any app is overridden by a plain assignment.
- **Variants are a function call.** A variant calls its base's build function with a few changed inputs, then assigns its own tweaks. Variants may be grouped in a public struct of the file (`personal.catppuccin.latte`), whose own `kosmos` is the group's name.
- **Nothing is written twice.** No full-file template copies of configs.
- **Anyone can support anything.** Apps and adapters are ordinary Zig packages: `kosm add <url>` and it works. Kosm's own are written exactly like third-party ones, with no private API.
- **Never wrong silently.** If kosm can't do exactly what was asked, it errors naming the kosmos, app, file and path involved, and writes nothing.
- **The user writes data, not plumbing.** No `io`, allocators, `environ`, `deinit` or cursors in user code.
- **Completion everywhere.** Everything a user sets is a plain struct field or function argument with a concrete type: no `anytype` patches, no `@Type`-generated types. Reflection is fine inside kosm.
- **Full words.** `Modifier`, `variations`, never `mod` or `vars`; Zig naming conventions.

## Vocabulary

- **package:** anything `kosm add` fetches; it may hold apps, adapters, kosmoi and a base kosmoi build on.
- **app:** support for one program (`kosm_hyprland` exports `App`, `from`, `App.apply`).
- **adapter:** support for one file format (Lua, TOML, JSON).
- **frontend:** support for writing in a language other than Zig (Lua), the way an adapter lets kosm write a format.
- **kosmos:** a rice, a function returning a tree of apps. It is what kosm applies.
- **base:** turns a look into apps; the official one is `kosm_base`, and a user's own base holds it and adds apps.
- **look:** what makes a base look nice (Krystallos, Everforest): a theme, fonts, the base's shared values, and a tweak of the official base's apps. A look builds no apps, so it works on any base holding the official one.

"Module" only ever means a Zig module.

## Architecture

```
 KOSMOS                  APPS                       ADAPTERS + WRITERS
 what the rice is   ->   what a program needs  ->   how bytes reach a file
```

- The layers never mix. Core data (colors, modifiers, the theme) knows nothing about apps or files. An app never parses a config and never does file IO; it only tells its `output` what to write, and reads files it builds others from (an installed icon theme) through it too. An adapter never knows about any app. The build enforces this where it can.
- **Inputs before `from`, tweaks after.** `from(inputs)` derives a complete struct of plain fields; any field can be assigned afterwards. To make a change flow into everything derived from it, change the input and call `from` again.
- **Lists outlive the function writing them.** A list of values known only at run time (a theme from an image or `Params`) is written `kosm.keep(T, &.{ ... })`, which copies it like `allocator.dupe` (`kosm.keepList` and `kosm.keepPrint` make a list of run-time length and text); lists of constants need nothing. Kosm refuses to apply a tree holding a list that points into a function that has returned, naming its path.
- **Kosm loads, the kosmos computes.** A kosmos does no IO: an image or file it names in its `Params` is read by kosm before the kosmos runs. Such a path starts with `~/` (home), `~~/` (the config), `~~kosmos/` (the applied kosmos' folder: a kosmos folder, or the folder holding a kosmos file) or `~~<name>/` (the folder of the package or local module of that name, so a look names its own wallpaper as `~~kosm_krystallos/...` wherever it is worn), or is absolute or relative. A relative default is relative to the applied kosmos' folder, a relative path a script kosmos gives to the script's folder, and a relative path on the command line to the working directory (and recorded absolute). A `~` naming no such folder is an error, and no module may be named `kosmos`. Once loaded, the kosmos sees the absolute path, which it may hand to any program.
- **A kosmos may fail with a message of its own** (`kosm.fail`), printed as given, so a script's file, line and path reach the user instead of a bare error name.
- **Nothing is written until kosm says so.** User code only builds values. Kosm calls every app's `apply`, plans every edit in memory, and commits all or nothing. `--diff` prints the plan and writes nothing.
- **Slow work runs on every core.** An app hands kosm many independent items (files to recolor, cursors to draw) and gets each one's result back; reading what many files hold now is spread the same way. Planning stays one call after another, in order, so a plan, its errors and its warnings are the same however the work was spread.

## Theme

`kosm.Theme` is the only thing every app receives: a palette, a mode, roles, code colors, diff colors, a background alpha and variations.

- **Palette:** black and white are required; the 12 hues of the wheel (red, orange, yellow, lime, green, teal, cyan, sky, blue, purple, magenta, pink, 30 deg apart) are optional, and a missing one is mixed from its nearest set neighbours by wheel position. Colors beyond the wheel belong to apps or to the kosmos' own constants.
- **Mode:** dark or light; the background and foreground roles follow it.
- **Roles:** libadwaita's names, which KDE and Material map onto, plus the few those add: background, foreground, accent, secondary, tertiary, link, visited, info, success, warning, error. Each is optional and defaults from the palette (the accent is cyan, the link follows the accent); an app reads the role, never the palette color it defaults to, so one assignment recolors every app. An app's own colors beyond these stay its own fields.
- **Code colors:** tree-sitter's capture names (comment, keyword, string, number, constant, function, type, variable, property, operator, punctuation, tag), each optional and defaulting from the palette or the roles (types from the secondary, tags from the accent), for editors and anything highlighting code.
- **Diff colors:** added, changed and removed, each optional and defaulting from the success, warning and error roles, for diffs, version control and anything marking changes.
- **Background alpha:** one alpha every app gives its own background, so a single value makes terminals, browser and editors translucent together.
- **Name:** the name programs show for the kosmos, falling back to the name kosm applies it under. One switch names the files a program picks by name: `kosm` for every kosmos, or after the kosmos so each keeps its own. Files a program includes by path are always `kosm`.
- **Built in levels:** a theme is built from its input (palette, mode, and the roles, code and diff colors the kosmos sets), in order: palette, roles, code colors, diff colors. A level's defaults come from the levels before it, and updating a level after changing the input redoes it and every level after it.
- **From an image:** a kosmos may take its palette and roles from an image named in its `Params`. Kosm loads the image (and caches what it read), so the kosmos only computes from it in plain code; a style says how colors are taken, readable against the background by default or exactly as in the image, or by a function of its own given each hue and the background.
- **Traits:** what a source of colors is like, as plain values every source gives alike: 0..1 measures (how busy, soft, glowing, flat, blurry, light, colorful, warm it is, and how much of each wheel hue it holds), a few colors (its glow's), and how opaque a window must be at each blur for text to read, measured against the colors the source itself gives. An image is one source; a package may add others (video), giving the same traits plus any of its own. A theme carries the traits of the source it came from, null for a theme made by hand, so any app may base its own choices on them (Hyprland's blur variant from how blue the picture is). Sources only describe; what a trait means for a value is decided by whoever reads it: an app for its own settings, a base or a kosmos for shared values, each value a weighted mix of traits through a curve into a range, every part with a default the user can change. Over those parts a mapping offers a few plain controls anyone can turn without knowing them (more frost, less opacity, always opaque), from a kosmos or as flags, and fit for a simple UI later.
- **Variations:** named color transforms in families (lightness, emphasis, state, surface, line, contrast, alpha), tweaked once on the theme for every app. A family of one's own is a struct of modifiers with defaults per mode, written in Zig or through a frontend; the theme cannot hold it, so a base holds it beside the theme and hands it to the apps reading it.
- Colors are OKLCH in f64. Modifiers also work in HSV, HSL, RGB and CMYK. A color outside sRGB is clipped when printed; `kosm colors` marks the colors that are.
- **Code of their own:** a modifier and a palette style may run a function of their own, written in Zig or through a frontend, with fields it declares; it goes wherever a modifier or style goes, and kosm exposes what its built-in ones use (keeping a color readable). It cannot fail, so a script's failure in it is recorded, and kosm fails with it before anything is written.
- **Shown as built:** `kosm colors <kosmos>` builds the kosmos as an apply would (variants, `Params`, scripts, `--set`) and prints every theme its tree holds outside its apps, which is how a tree says what it wears; it writes nothing.

## Rules for apps

- A field mirroring a program's setting keeps the program's name, in Zig casing (`kitty_mod`). Null means "not written; the program's default applies".
- `from(theme)` fills fields from the theme; an `App{}` without `from` writes nothing. Fields derived from another field of the same app (an inactive color from the active one) are null until `apply`, so assigning the source still flows into them and assigning the derived one still wins.
- A program's separate opacity setting follows its background's alpha; the background is one color with alpha, never a color plus an opacity value.
- Every app has `extra` for settings it doesn't cover, written after its own and failing if one overlaps a set setting.
- An app may write a whole folder it owns (an icon theme), its symbolic links included; diffs and reports show such a folder as one line. A link replaces only a link, never a file.
- An app writes its own file that the program includes, rather than the program's main config. Making the program read it is the user's job, except for an app's own visible include block, or the one entry an app adds to a program's list of includes (Vicinae's `imports`), both of which the user can turn off. Kosm never creates backups.
- Each written file has a `kosm.Format` (color spelling, booleans, float precision) layered from the user's assignment, the app's default, the adapter's and kosm's.
- An app may reload its program after a successful apply, and set there what a program keeps outside files (gsettings); a failure is a warning. It reloads only when one of its files or links changed, or always when it writes none, so an apply changing nothing disturbs no program; `--reload` reloads every app.
- A browser extension reaches a running browser through `kosm relay <file>`, a native messaging host the browser starts and stops: it sends the file an app wrote whenever it changes. Kosm runs nothing while the browser is closed.
- An app's package exports the adapters it writes with, so a config needs only that package to rice the program.

## Rules for adapters and edits

- An adapter declares only what it can do (`serialize`, `parser`, `format`, `comment`); kosm says clearly when an app needs a capability an adapter lacks.
- Edits are byte-preserving: only a value's own bytes change, and unchanged files are not rewritten. Two apps writing the same bytes is an error.
- A path that matches nothing is an error; setting a value never inserts its key. A path matching several values must say which (`setFirst`, `setAll`, `setNth`).
- An app may add a key or list entry it names itself, only so the program reads the app's own file (an include), keeping the file's comments and layout.
- Kosm core owns the tree-sitter runtime; an adapter ships only its grammar. A grammar is a dependency like any library. Simple formats are hand-written instead.

## Packages and the config project

- A config project (`~/.config/kosm`, made by `kosm init`) is a Zig project depending on `kosm` by URL; `kosmoi/`, `apps/`, `adapters/`, `frontends/` and `colors/` (modifiers, palette styles and variation families) hold the user's own. A file there is private to its directory; a directory with `root.zig` is a package.
- Package commands (`kosm add`, `remove`, `update`) wrap `zig fetch`; `packages.zon` remembers the ref to follow.
- `kosm.zon`, optional and written by hand, holds kosm's own settings for a config. Its `build` picks the kosmoi `kosm build` compiles ahead of an apply: every one in `kosmoi/` (the default), only some, or all but some; the command line can replace that choice for one run. Its `optimize` says how they compile: debug by default, since that compiles in seconds where an optimized build takes minutes, while an apply stays under a second; optimized with safety checks (or without them) for the fastest apply.
- Zig never deletes from its caches, so kosm does: `kosm update` deletes the config's cache when a package changed, since every executable recompiles then anyway, and `kosm clean` also deletes package versions no manifest uses any more. The cache goes whole or not at all: Zig's manifests point into it. Zig's global cache is shared with other projects and never touched.
- Kosm's own packages live in repositories of their own, like anyone's. `kosm init` adds every official package to a new config, with a starting kosmos that uses them.
- The base kosmos is the package `kosm_base`: `from(look, apps)` returns the official apps chosen, each an optional field, and the theme they were built from, then applies the look's tweak; `kosm apply kosm_base` wears every app in its default look. Its default look is literal: black is `#000000`, red `#ff0000`, rounding 0. Its shared values (rounding, gaps, border, padding, cursor, keyboard layouts and the like) are set once and read by every app with that setting; a value is shared once two apps use it or very likely will. Personal settings (shaders, keyboard layouts, editor) default to null, so the program's own default applies.
- A kosmos chooses its base, its look and its apps (all, none, only some, or all but some; the others are never applied), then assigns its overrides. Overrides given as loose values (a script's tables, `--set`) for an app it did not choose are checked against the app's fields, then dropped, so a kosmos may keep settings for every app it ever uses. A user's own base holds `kosm_base`'s in a struct of its own beside its added apps, which follow the look through the theme's roles. The starting kosmos builds on `kosm_base`.
- One package per language, `kosm_<language>`, holds everything kosm does with it: its adapter and its frontend, each a Zig module of its own (`kosm_lua_frontend`). The frontend's own dependencies (an interpreter) are lazy, fetched and built only by the script runner, so an app depending on such a package only for its adapter never fetches them.
- A package may be written through a frontend: its repository holds a root script (`root.lua`) and no `root.zig`, beside the one-line `build.zig` and the `build.zig.zon` every package has, which depends on kosm and on the package of its language. Its root gives one app, adapter, frontend, modifier, palette style, variation family or kosmos, or values for building on (a look, a base), which its frontend tells from what the script returns; the package's own build generates its Zig module, as a config's build does for `apps/`, so Zig kosmoi and packages use it like any other, and it uses Zig packages' types like any script app. A kosmos there is the package's own, applied and built on by the package's name like a Zig package's `kosmos()`. Its script is found when kosm runs through the package's folder, also when the config reaches the package only through another one. `kosm new package <name> [--language <frontend>]` scaffolds one, holding an app, in a folder of its own in the working directory, pinning kosm and the frontend's package as the config does.
- A build holds one copy of each package: what a config (or a package built on its own) lists itself wins over the copy a package pins, and packages pinning different copies of a package it doesn't list fail the build naming them.
- Zig is pinned to a tagged release, never master.

## Kosmoi, apps and adapters written through a frontend

- **Every language is equal.** A kosmos, look or base is the same whatever language it is written in: called with its inputs, it gives a value the caller builds on, and any of them, in any language, builds on any other. What one language reaches, every frontend reaches; a frontend adds only syntax, and idioms where they read better in its language (Lua methods, variants as functions). Zig is the natural choice for low-level code (adapters, formats), but nothing requires it: apps, adapters and every other part of kosm can be written through any frontend whose own code is Zig.

- A **script kosmos** is a file `kosmoi/<name>.<extension>` that the frontend claiming its extension reads into loose values; its name is unique among every kosmos, module and package. It may give variants as functions, which `kosm apply <name>.<variant>` builds. A script in a Zig kosmos' folder (`kosmoi/personal/nord.lua`) is one of that kosmos' variants (`personal.nord`), built on its parent as any script builds on anything, and listed, completed and applied like its Zig variants. A folder may give its kosmos through a script instead: `kosmoi/frost/root.lua` is the script kosmos `frost`, and a `root.zig` beside it gives only variants (`frost.iced`); a folder holds one root per language, exactly one of which gives the kosmos. A variant's name is unique across languages: a frontend lists the variants a script gives without running them, so kosm refuses one sharing a name. kosm core knows no frontend language, only the interface every frontend implements.
- A script builds on a Zig kosmos or base (setting its `Params` below the command line's, then values on its tree), on another script, or on nothing: then it gives a theme input, and every app of the config that a theme alone builds is chosen by naming it. Or it builds its tree itself by calling Zig code, and returns it: a tree a Zig kosmos returns, or a struct of apps a package or kosmos declares at its top (a base, `kosm_base.Base`).
- A Zig kosmos builds on any other kosmos, Zig or script, by naming it in a `kosm.Kosmos(Tree)` field of its `Params`: kosm builds it before calling the kosmos, as it loads an image, and the kosmos takes a copy of its tree, which must be a `Tree`. A flag or a script names another one. Kosmoi building on each other in a circle fail naming it.
- A script calls Zig code: every Zig kosmos (`kosmoi.personal(params)`), and every public function and value of `kosm` and of each module whose parameters a script can give, found by reflection, so package authors write no bindings. A value a call returns stays a typed Zig value the script holds by reference: setting its fields sets them as an assignment would, and giving it to a call or a field copies it.
- What a base, look or kosmos exports for building on takes ordinary values known at run time (a look, a theme), never compile-time ones, so every frontend can call it.
- A frontend spells any Zig name its language reserves the way that language reads best (Lua: `end_` for a parameter, `["end"]` for a field), so kosm and packages name things for Zig alone.
- A script reaches no files, environment or programs: its frontend gives it only the language's libraries that compute.
- Errors name the script's line for every value it gives, and a value the script writes but the language reads as nothing (Lua's `nil`) fails instead of being dropped.
- Scripts are read when kosm runs, like a file named in `Params`: editing one never compiles. One runner, holding every Zig kosmos, app and frontend of the config, runs every script and every Zig kosmos building on another; it is rebuilt only when Zig code it is built from, or what a script declares (an app's fields, the values a kosmos exports), changed since it was last built.
- An **app written through a frontend** is `apps/<name>.<extension>` or `apps/<name>/root.<extension>` (a folder holds one root). Its script declares the app's fields in a table built from kosm's type constructors (`bars = kosm.integer(0)`, `foreground = kosm.optional(kosm.Color)`, any Zig type by name, `cursor = kosm_cursor.App`), each documented by the comment above it, and gives `from(theme)`, `apply(self, output)` and optionally `reload(self, reloader)`. It keeps every rule of an app: it does no IO and never parses.
- The frontend reads the declaration without running a function, and the build generates a Zig module from it, with `App`, `from` and `App.apply` calling into the script and the doc comments, at a fixed path and rewritten only when it changes. So the app is used from Zig and scripts alike, completes in every editor, and editing a function body compiles nothing; only a changed declaration rebuilds.
- Its functions keep a Zig app's signatures: `from(theme)` returns `App` and never fails, so a script error there is recorded like `kosm.fail`'s message, and kosm fails with it (script, line, message) once the kosmos returns, before anything is planned. Only the runner of scripts runs them, through a host it installs once as a global, since `from(theme)` takes nothing to hand it in; a Zig kosmos wearing such an app is applied by that runner. A frontend keeps one interpreter for every app's script, each script with globals of its own.
- A **modifier, palette style or variation family written through a frontend** is `colors/<name>.<extension>` or `colors/<name>/root.<extension>`; the frontend tells which from what the script returns. Its script declares its fields as an app's does and gives `apply(self, color)` (a style's `apply(self, hue, background)`); the build generates a Zig module from the declaration, whose `modifier(fields)` gives a `kosm.Modifier` (a style's `style(fields)` a `kosm.Image.Style`), so Zig and scripts use it alike. A **variation family** there declares its modifiers and gives `from(mode)`; its module gives `Family` and `from(mode)`. Only the runner of scripts runs any of them, so a kosmos reaching one is applied through that runner.
- An **adapter written through a frontend** is `adapters/<name>.<extension>` or `adapters/<name>/root.<extension>`. Its script gives the adapter's name, extensions, comment syntax and default format as plain data, and any of its capabilities as functions; values, nodes and byte ranges cross as plain tables in the language's own counting (Lua's ranges count from 1 and end on their last byte). As for an app, the build generates a Zig module from what it declares, so Zig and script apps write through it alike, and editing a function compiles nothing. Only the runner of scripts runs it, so a config holding one applies every kosmos through that runner.
- A **frontend written through a frontend** is `frontends/<name>.<extension>` or `frontends/<name>/root.<extension>` (a Zig module there gives frontends as one in `adapters/` does). Its script gives the frontend's name, extensions and editor file as plain data, and `load`, `variants` and `complete` as functions; as for an adapter, the build generates a Zig module from what it declares, and only the runner of scripts runs it. What crosses is plain tables, and a value `load` returns carries the place in the kosmos it was written at (`kosm.at` in Lua), so errors name the kosmos' line. It reads kosmoi only: apps, adapters and the rest are never written in its language, since reading them would need the build to generate modules in two rounds for little gain; a language wanting them is a frontend written in Zig. The files it writes stay inside its completion folder.
- A kosmos script in `kosmoi/` exports values as a package's root script does, so a look written in a script is worn by any kosmos of the config (`krystallos.look()`). Its module gives them, the kosmos and variants it exports are applied like a Zig kosmos', and the scripts in its folder are their variants.
- A package's root script may **export values for building on**, each typed as in Zig: a value of a Zig type its function builds (a look: `look = kosm.value(kosm_base.Look, function() ... end)`), the base it declares (its apps, declared as an app's fields are) with a `from` naming the types it takes (`kosm.takes(kosm_base.Look, function(look) ... end)`), and its kosmos as such a value. It declares any other struct the same way (a kosmos' `Params`, its fields' Zig types taking defaults as tables), and a function taking one (`image = kosm.takes(Params, function(params) ... end)`) is a variant with those `Params`, which kosm loads and fills from flags as for a Zig kosmos. The package's module gives each as a function (`kosm_frost.look()`, `from(look)`, `kosmos()`) and the base as its type, so Zig and scripts use them like a Zig package's; a script's look is a function where a Zig look is a constant, as both work. A function inside a value it gives (a look's `tweak`) becomes a Zig function of its place, calling the one the script gave there last. None of them can fail, so a script's failure is recorded and kosm fails with it before anything is planned; only the runner of scripts runs them.
- A script calls the same API under the same names as Zig (`output:generateValue(...)`); a Zig method taking a compile-time shape (`generate`, `block`, `template`) has a form taking a `kosm.Value` for values built at run time.
- `kosm new <kind> <name> --language <frontend>` writes a single script from the scaffold that frontend gives for the kind as plain text, so kosm core still knows no language; without `--language` it scaffolds a Zig package. Its kinds are kosmos, app, adapter, frontend, package, and the modifier, palette style (`style`) and variation family that go in `colors/`.
- Completion for scripts is generated when that runner is built, into the config's `zig-out/completions/<language>/`, from every type a script may set and every function it may call, with the doc comments of their Zig source; a type keeps its Zig name. One editor file in the config (`.luarc.json` for Lua) points at it; kosm creates it where it is missing and never rewrites it.

## Non-goals

- Inserting the keys a path names (`set`, `--set`), or includes beyond an app's include block or its own include entry.
- Backup files.
- Checking package versions against the user's kosm.
- `**`, predicates or regex in paths.
- `.with` / `.override` patch APIs.
- Any custom configuration language.
- LSP integration.
